## Conventions to follow

1. **Standalone components only**, Angular 18 style: `standalone: true`, `imports: [CommonModule, ...]`, new control-flow syntax (`@if`, `@for (x of list; track x.id)`, `@else`) — not `*ngIf`/`*ngFor` structural directives, not NgModules.
2. **Split `.ts` + `.html`** files per component (like the existing examples), not inline templates, except for tiny one-off components (~10 lines) where inline `template:` is fine.
3. **Lazy-load everything** via `loadComponent: () => import(...).then(m => m.XxxComponent)` in route files — never eagerly import feature components into route files or into each other.
4. **Reuse mock data services** where the domain overlaps (clients, transactions, schemes, commissions, notifications). If your module needs new domain data with no existing model (e.g. audit trail filters, campaign templates, FX rates, document vault entries), add a **new** mock-data file under your own feature folder (e.g. `features/admin/admin-data.mock.ts`) and a small local service or plain exported const — do NOT edit the shared files under `core/mock-data/` or `core/services/` (other agents are working in parallel; shared-file edits will conflict). It's fine to duplicate a tiny bit of mock data locally rather than touch shared files.
5. **Realistic Indian fintech mock data**: INR amounts, Indian names/companies, AMC/scheme names consistent with what's already in `core/mock-data/schemes.mock.ts` and `clients.mock.ts` (feel free to reference the same clients/schemes by id for cross-linking, e.g. a client-detail page can pull from `ClientService`).
6. **Currency formatting**: use the `inrCompact` pipe for large aggregate figures (AUM, totals) and `{{ value | number }}` with a `₹` prefix for precise amounts (units, per-transaction values), matching the existing dashboard's pattern.
7. **Navigation**: use `routerLink` for internal links; wire buttons that logically lead to another existing route (e.g. "View All" style links, or into a flow like `/mf-purchase/select-scheme`) — don't leave dead buttons where a real destination already exists elsewhere in the app.
8. **No `ComingSoonComponent` left behind** for any route you were asked to build — replace every stub in your assigned route file with a real `loadComponent`.
9. **Don't touch**: `app.routes.ts`, `nav-configs.ts`, `layout.models.ts`, anything under `core/layout/`, `core/services/`, `core/mock-data/`, `shared/components/stat-card`, `shared/pipes/`, or any other feature module's folder/routes file outside the one(s) you were assigned. If you find a bug in shared code, note it in your final report instead of fixing it directly.
10. **Verify your work compiles**: after building your screens, run `cd c:\dev\wealthos-app && npx ng build 2>&1 | tail -80` (Bash/PowerShell — Windows path, use the shell style available to you) and fix any TypeScript/template errors before finishing. The dev server (`ng serve`) may already be running in the background on port 4200 with hot-reload — you don't need to start your own unless it's not running.
11. Keep components **reasonably concise** — real, functional, visually faithful to the mockup's layout and information density, but you don't need to transcribe every pixel/class from the original static HTML. Prioritize: correct data binding to mock services, correct navigation, correct use of shared design tokens, faithful layout structure (cards, tables, charts-as-SVG/CSS same style as the portfolio dashboard example).
